# 第 3 阶段：中国交付专项计划

状态：`in-review`

## 1. 阶段目标

把“中国交付适配”建设成可执行的需求澄清、适用性判断、证据收集、审批、上线与复核流程，而不是法规清单、厂商排名或合规保证。

本阶段补齐三类净新增能力：

1. 中国场景适用性分流：服务对象、责任主体、部署区域、模型来源、数据流、输出用途，以及是否驱动决策或行动。
2. 国内模型与 MaaS 决策面：区域、交付、版本、采购、数据与日志、配额、SLA、评测、回滚、路由和退出。
3. 多模态内容生命周期：生成、审核、标识、发布、撤回、申诉、事件和证据留存。

本阶段只处理中文内容。具体法规、产品和市场事实必须在执行时重新联网核验，本计划不预写当前结论。

## 2. 进入条件

- Stage 0 中路由到 Stage 3 的候选和 `approvedScope` 已经确认。
- 第 2 阶段稳定机制 owner 已经明确，避免重复建设。
- 中文单线发布契约已经实现并有有效 `localeGateReceipt`；否则只允许研究，不允许中文语义写入。
- 当前分支为 `codex/ai-knowledge-base-content-improvement`，工作区、HEAD、正式基线和前一批 receipt 一致。
- 用户确认进入高风险研究阶段。
- 对具体法律义务的表达有可用的人工或专业 Review 路径。

### 2.1 研究授权门

只读研究允许候选处于 `research-required` 或 `expert-review-required`，但必须具备：

- 用户明确的研究授权和冻结场景。
- Stage 0 候选 ID、批准研究范围、风险与证据状态。
- 当前 owner、已有 `sourceId`/`claimId` 和前置阶段 receipt。
- 研究日期 `asOf` 和官方来源优先协议。

研究门只允许联网核验、来源矩阵、结论卡和风险发现，不修改公开内容。

### 2.2 正式写入门

中文写入必须同时满足：

- 用户已 Review 拟写结论及其边界。
- `evidenceGate=pass`，owner 已解决，Claim 方案完整。
- `localeGate=pass` 且英文 authored 与有效内容基线已冻结。
- 法律、安全或行业 high/critical 问题均已解决或保持 hold、不进入正文。
- 研究没有超出 `approvedScope`；若范围、主体、owner 或证据结论变化，先退回用户裁决。

## 3. 现有基础与净新增

### 3.1 直接复用

- AI Governance 已有 Register → Tier → Assess → Assign → Evidence → Decide → Operate → Reassess 治理链。
- Security 已有不可信输入、授权检索、证据约束建议、确定性授权执行和恢复路径。
- Model Landscape 已有 provider、endpoint、region、version、delivery、config 候选元组，以及硬约束、试点、回滚和退出。
- Multimodal 已有生成、审核、标识、发布和证据保留管线。
- Solution Patterns 已有业务结果、最小充分闭环、阶段门、运营和退出。
- 已有中国生成内容标识 Claim 和官方来源只能复用或更新，不能创建语义重复项。

### 3.2 真正净新增

- 面向中国交付的统一适用性问卷和审批证据包。
- 法规义务、工程控制、运营证据和责任人的映射方法。
- 中国区域模型与 MaaS 的采购、运行和退出决策面。
- 内容发布后的撤回、更正、申诉和事件闭环。
- 对法规状态、模型目录、区域、版本、价格和配额的正确 Claim 分流。

### 3.3 明确排除

- 不把目标库法规摘要、厂商表格或回流内容当正式证据。
- 不建立第二份模块、问题、Reference 或 Claim 注册表。
- 不新增“中国 AI”独立模块或路由。
- 不写模型排行榜、永久推荐、固定价格或无有效期的能力承诺。
- 不把工程检查表写成法律意见或合规结论。
- 不修改英文内容。

## 4. 模块责任边界

| 模块 | 主责 | 不负责 |
| --- | --- | --- |
| AI Governance | 使用目的、主体、风险分级、审批、例外、申诉、复核 | 技术控制实现、法律终审 |
| Security | 威胁路径、技术控制、红队、隔离、恢复、事件证据 | 接受业务风险、裁决法律义务 |
| Model Landscape | 模型、区域、交付、版本、评测、路由、回滚、退出 | 厂商背书、法规解释 |
| Multimodal | 内容来源、生成、审核、标识、发布、撤回和溯源 | 企业审批权 |
| Solution Patterns | 业务结果、角色、交付、验收和退出 | 重复维护法规或模型目录 |
| Data Engineering | 数据分类、来源、血缘、跨区域路径和删除传播证据 | 法律分类终审 |
| AI Ops | 发布、观测、变更、事件、恢复和运行证据 | 业务审批 |

完整方法只能在一个主模块出现，其他模块通过“相关模块”和稳定关系连接。

## 5. 官方法源研究协议

### 5.1 先冻结场景

每次研究前填写场景卡：

- 服务对象与所在区域。
- 服务提供者、模型提供者、部署者和业务责任人。
- 公网、企业内、专有部署或第三方 MaaS。
- 模型、检索、工具和数据的位置。
- 是否包含个人、敏感、重要或客户受限数据。
- 输出是生成、推荐、决策支持还是自动行动。
- 是否影响权益、资金、资格、安全或公共服务。
- 是否存在跨境、跨区域、第三方共享、公开发布或外部分发。
- 是否需要人工审批、申诉、撤回和事件通报。

场景未冻结，不得形成“适用或不适用”的公开结论。

### 5.2 来源优先级

1. 官方现行法律法规、部门规章、强制性标准和正式规范。
2. 官方实施通知、解释、问答、办事指南和主管机关公告。
3. 地方主管机关正式文件。
4. 官方产品文档，只证明产品能力、区域、版本和配置。
5. 原始论文和权威标准。
6. 律师解读、厂商文章和行业材料只用于发现线索。
7. 目标库只用于发现关键词和待核问题。

高风险准确性要求在执行时浏览最新官方来源。研究卡保存官方 canonical URL；正式模块只引用稳定 `sourceId`，公开链接统一由 `app/reference-content.mjs` 和 `/references` 提供。

### 5.3 法源摘录卡

每项候选规则记录：

- 研究冻结日期 `asOf`。
- 候选 sourceId。
- 官方 canonical URL、文件编号和条款定位。
- 发布机关、司法地域、文种和正式或征求意见状态。
- 发布、生效、过渡和废止日期。
- 受规制主体、适用地域和触发条件。
- 原文条款或准确定位。
- 义务、例外、过渡安排和替代关系。
- 对应工程控制和应留存证据。
- 仍需法律、隐私或行业专家确认的问题。
- 核验日期和下次复核日期。

每个拟写结论还必须有稳定 `conclusionId`，并形成 `conclusionId → sourceId → 条款 → 主体/触发/例外/时间 → reviewer` 映射。无法确认现行状态、主体或例外的结论保持 hold。

摘录只保留必要短句，其余使用准确转述，遵守来源版权限制。

### 5.4 冲突处理

按以下顺序裁决：

- 法律层级。
- 正式文本优先于草案。
- 现行文本优先于已替代文本。
- 精确适用范围优先于泛化摘要。
- 原始官方材料优先于二手解读。

无法消除的冲突标记为 research-only 或 hold，不进入确定性正文。

## 6. 高风险审查

以下任一条件触发人工高风险审查：

- 输出影响资格、雇佣、信贷、保险、医疗、公共服务、资金或人身安全。
- 系统能自动执行不可逆动作。
- 涉及敏感信息、重要数据、未成年人或跨境流动。
- 拟使用“必须、禁止、已合规、无需备案”等确定性措辞。
- 法源状态、责任主体、例外或过渡期不清楚。
- 用产品能力推导法规适用性。
- 依赖非官方期限、办理时间或从业经验。

审查至少覆盖业务责任、法律或隐私、Security、Governance 和运行责任。每项发现记录 finding ID、风险领域、严重度、影响对象、reviewer、owner、处置、支撑来源或测试以及复核日期。

允许的处置为 `resolved`、`accepted-with-boundary`、`hold` 或 `blocked`。未解决的法律适用性、主体、自动化最终决定、敏感数据、跨境、越权或不可逆动作问题直接阻止写入。证据或专业确认不足时，正文只能表达需要核验的问题、触发器或风险。

## 7. Claim 分流

| 内容类型 | 处理 |
| --- | --- |
| 稳定机制、决策方法、责任边界 | 写正文，不为凑数建 Claim |
| 法规状态、生效日期、适用时间线 | 原子 Claim，优先官方来源，通常 90 天；过渡期可缩短至 30 天 |
| 已公告未生效或待替代规则 | watch，复核日不得晚于计划生效日 |
| 模型目录、区域、版本、价格、配额、产品规格 | 每个变化面单独 Claim，30 天复核 |
| 官方产品文档 | 只证明能力或配置，不证明客户合规 |
| 二手解读或从业估计 | 研究线索，不形成确定性卖点 |
| 客户专属数据、流程和 SLA | 留在项目交付物，不进入公共 Claim |
| 已有中国内容标识规则 | 更新或复用现有 Claim，禁止重复 |

所有 URL 只进入 app/reference-content.mjs；模块正文只引用稳定 sourceId。

## 11. 单批执行流程

1. 冻结 Git 与内容基线。
2. 建立场景卡，不带场景不研究法规适用性。
3. 并行只读执行法源、技术控制和当前覆盖工作包。
4. 主 Agent 合并来源、适用范围和冲突。
5. 先提交来源矩阵和拟写结论供用户 Review。
6. 主 Agent 串行写中文正式内容。
7. 对抗式复核主体、地域、时间、例外、责任和不可外推。
8. 更新 Reference、Claim、问答、证据、术语和中文更新时间。
9. 运行定向检查、中文单线门禁和 npm run check。
10. 提交用户 Review；当前批完成后再进入下一批。

每批生成统一 receipt，记录 `stageId`、`batchId`、基线 SHA、范围哈希、输入候选与前置 receipt、批准范围、`sourceIds`、`claimIds`、受影响对象、locale 影响、测试结果、风险发现、开放问题和用户 Review 类型。

研究确认、拟写确认和最终合并/发布确认必须分开记录。本阶段默认只形成专项分支检查点；只有用户明确改变本计划、要求中途提前成为正式版本时，才另行进入完整发布门。

## 14. 完成标准

- 每项法规结论能回到官方来源、适用范围和核验日期。
- 主体、触发条件、例外和生效状态明确。
- 不出现“使用某产品即合规”。
- 动态事实进入 Claim，过期或范围不明内容不作为卖点。
- 现有中国内容标识 Claim 未重复创建。
- 模块责任无冲突，完整故事只有一个 owner。
- 问答、证据卡、Reference 和中文更新时间同步。
- 不新增模块、路由、第二注册表或英文内容。
- 高风险项完成人工 Review，未解决项保持 hold。
- 定向检查和 npm run check 通过。
- 英文 authored 内容、英文有效内容和英文日期保持最后真实基线。

如果本阶段产生经用户确认的内容变更，只在 `codex/ai-knowledge-base-content-improvement` 形成经验证的本地批次检查点和 receipt；不合并 `main`、不推送、不发布。仅研究或全部 no-op 时只保存回执。最终发布统一遵守总体计划的分支合并门。

## 15. 停止条件与 Stage 4 交接

以下任一发生即暂停：

- HEAD、远端、seal、范围哈希或关键文件摘要漂移。
- 官方法源不可访问、文本状态冲突、适用主体不清或 Claim 已过期。
- high/critical 风险未解决，或必要专业 Review 不可用。
- 研究结论超出已批准范围，改变场景、owner 或目标合同。
- locale gate 失败、延期未登记或英文有效内容变化。
- 定向检查或 `npm run check` 失败。

Stage 4 只接收已经确认的候选 ID、有效来源与 Claim receipt、稳定控制 owner、已解决高风险项和明确 hold 清单。Stage 3 未完成的法律或中国适用性问题不能在行业蓝图中绕过。
