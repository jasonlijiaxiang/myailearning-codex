# 第 2 阶段：稳定内容补强计划

状态：`in-review`

## 1. 阶段目标

吸收对照库中真正净新增、低时效、能够改变客户判断的稳定机制与教学结构，同时保持当前库的内容 owner、证据和质量门禁。

本阶段主要补强：

- 方案交付中的客户责任、验收和退出设计。
- Data 与 Infra 的诊断式售前方法。
- Agent 现有 Sub-agent Runtime 默认 no-op；真实候选是低代码边界和 Memory Poisoning。
- Evaluation 的基准适用范围。
- RAG 的多模态路线与分段诊断。
- Multimodal 的取消和状态恢复。
- MCP 的真实报文教学形式，仅在确认存在缺口时采用。

不处理中国法规、国内平台实时状态、价格、排名和其他高频动态内容；它们属于第 3 阶段。

## 2. 进入条件

必须同时满足：

1. 第 0 阶段差异矩阵已经完成并经用户确认。
2. 第 1 阶段现场层已经完成，或明确确认不会与本阶段冲突。
3. 本阶段每个写入候选都来自 Stage 0 用户裁决后的最终路由。
4. 当前分支为 `codex/ai-knowledge-base-content-improvement`，工作区和本地基线符合专项范围。
5. 前一模块打磨批次 seal receipt 与当前 HEAD 一致。
6. 中文单线发布契约已经 Review 并具备可执行方案。

最后一项是硬门。当前 npm run check 会校验中英文问答数量、证据关系、内容哈希和共享更新时间；不能在修改中文正文后简单跳过双语门禁或生成虚假的英文 PASS 记录。

### 2.1 Stage 0 路由输入

Stage 2 不直接消费研究者的 `recommendedAction`。写入候选必须同时满足：

- `targetStage=stage-2`。
- `reviewDecision=approved`，或 `approved-with-changes` 且 `approvedScope` 已冻结。
- `finalAction=implement`。
- `executionReadiness=ready`。
- `evidenceGate=pass`。
- `ownerStatus=resolved`。
- `localeGate=pass`，并有有效 `localeGateReceipt`。
- 所有 `prerequisites` 已满足，`blockingQuestions` 为空。

`finalAction=research` 只生成只读研究包。研究结果通过证据门后必须重新提交用户裁决，不能在批次内部自动升级为写入。

机器输入使用 Stage 0 生成的 `stage-2-5-routing-pack.json`；Markdown 只用于 Review。

## 3. 内容纳入门

每项新增内容必须回答：

- 它支持哪个客户决策？
- 当前库缺的是机制、边界、案例、诊断还是取用方式？
- 主模块 owner 是谁？
- 现有内容能否通过改写或扩展完成，是否真的需要新块？
- 有什么失败模式或不可外推边界？
- 哪些一手或权威来源支持？
- 是否会引入动态 Claim？
- 是否需要同步问答、证据卡、课程、实战或术语？

仅仅更口语、更有图感或对照库写得更长，不构成正式新增理由。

## 6. 第 2A 批：方案与交付诊断

### 6.1 Solution Patterns

主 owner：solution-patterns。

该模块是组合 owner：基础内容与 FinOps 贡献可能来自不同文件，并由共享组装层合并。批次工作包必须先解析真实 owner 和合并路径，不能因为表面模块归属而重复建立“三本账”或平行内容。

当前模块已经覆盖最小充分闭环、阶段门、完整成本、单位经济和退出。以下只是逐项 diff 的候选边界，不新建平行方法论：

#### 客户侧责任四角

- 业务决策人：确认业务结果、损失函数和是否进入下一阶段。
- 数据与 IT Owner：提供数据、身份、权限、系统接口和运行环境。
- 知识与口径运营人：维护规则、术语、评估样本和争议处理。
- 安全与合规签字人：确认上线条件、责任和专业复核。

内容必须说明角色可以由同一人兼任，但责任不能消失。

#### PoC 契约

- 使用代表性真实数据或明确限制的合成数据。
- 预先签字的成功、失败和停止指标。
- 明确基线、范围、预算、责任和验收线。
- 定义 PoC 通过后如何进入生产验证，失败后沉淀什么。

#### 三本账

- Token 或模型调用账。
- 并发、容量和服务等级账。
- 人工建设、运营和复核账。

三本账必须连接单位经济和客户结果，不给脱离工作负载的统一比例。

#### 周期与客户准备度

- 数据是否到位。
- 接口与环境是否可用。
- 指标和责任人是否确定。
- 安全、采购和法务是否进入。

周期只写决定因素，不承诺固定周数。

#### 可替换件与沉淀资产

- 可替换件：模型、工具、框架、部分平台能力。
- 客户沉淀资产：指标口径、评估集、权限映射、数据契约、Runbook、退出脚本和决策记录。
- 说明哪些托管能力可能难以迁移。

#### 验收与退出

- 业务结果、质量、安全、可靠性、成本、运营六类验收面。
- 人工接管与权威业务状态。
- 供应商切换、模型退役和数据/日志迁移。
- 失败时可恢复状态与客户可带走资产。

### 6.2 Data Engineering

主 owner：data-engineering。

补充“数据就绪分诊”，而不是增加通用成熟度分数。

#### 数据就绪问题

- 数据能否合法、稳定地访问。
- 对象是否有稳定身份、版本和删除语义。
- 权限是否能传播到索引、检索、生成和日志。
- 数据质量是否足以支持目标任务和评估。
- 变更、删除和纠错能否进入运行流程。

#### 连接器五项契约

- 认证与授权。
- 初始同步与增量同步。
- 删除、撤回和权限变更传播。
- 失败、重试、幂等和恢复。
- 观测、审计和责任归属。

#### PoC 缩小范围

当数据未准备好时，给出缩小到单一来源、有限对象、明确 ACL 和可回放评估集的路径，而不是假装完整数据工程已经成立。

### 6.3 AI Infra Compute

主 owner：ai-infra-compute。

补充“先排约束、再谈卡”的售前顺序：

- 工作负载合同：训练或推理、模型、精度、序列、并发、质量、SLO 和增长。
- 设施条件：电力、散热、机架、布线和故障容量。
- 内存与数据路径：HBM、KV Cache、存储、检查点和加载恢复。
- 通信：Scale-up、Scale-out、网络和拓扑。
- 软件与运维：驱动、运行时、框架、镜像、监控和升级。
- 供应连续性：设备交付、替代、云上补充和退出。
- TCO：设备、空闲、失败重跑、存储网络、能源和人工。

明确拒绝“利用率达到某百分比就自建”或“几张卡即可”的通用口袋结论。

## 7. 第 2B 批：Agent 与 Evaluation

### 7.1 AI Agent

主 owner：ai-agent。

#### Sub-agent Runtime

当前已经覆盖委托契约、最小上下文、权限默认不继承、fan-out、深度、预算、父 Agent 验证以及 Handoff、Agent-as-tool 与 A2A 的区别。默认处置为 covered / no-op。只有第 0 阶段证明存在新的客户判断时，才局部补强：

- Sub-agent 是运行时与编排能力，不是新的模型类别。
- 任务书必须自包含，明确目标、输入、权限、预算和终态。
- 子任务使用独立上下文，避免无界共享主对话。
- 结果通道保持窄而结构化。
- 限制深度、并发、Token、工具和时间。
- 父运行负责取消、重试、合并、冲突和最终业务状态。

与现有多 Agent、工具权限、Run 状态和终态内容连接，不重建 Agent 主骨架。

#### 低代码与 Code-first

只提供决策维度：

- 状态和分支复杂度。
- 自定义工具和协议深度。
- 测试、版本、调试和审计需求。
- 性能、隔离和部署要求。
- 迁移、导出和退出能力。
- 团队技能与运营责任。

不提供“满足两个条件就必须下沉”等伪精确规则。

#### Memory Poisoning

- 写入源和信任边界。
- 记忆提取、摘要、归并和检索链。
- 恶意或错误内容如何持久化并影响未来运行。
- 来源、作用域、TTL、审批、隔离、删除和重建。
- 将实验攻击成功率与生产发生率分开。

Agent 负责运行机制，Security 作为相关模块负责控制与攻击面，正文不能重复两份。

### 7.2 Evaluation

主 owner：evaluation。

增加 Benchmark Atlas，但只回答：

- 基准测量的对象和能力。
- 适合哪一轮筛选。
- 数据、工具、环境和评分条件。
- 不能证明的生产结论。
- 与客户任务、Estimand、重复试验和终审的关系。

公开正文保留稳定分类。基准版本、当前榜单和领先分数进入 Claim 或不写。

必须避免：

- 把模型榜单当作客户任务验收。
- 把单次成绩当作稳定能力。
- 忽略污染、工具版本、运行环境和统计不确定性。

## 8. 第 2C 批：RAG、Multimodal 与 MCP

### 8.1 RAG

主 owner：rag。

#### 多模态检索三路线

- Caption 或结构化文本索引。
- 统一多模态嵌入。
- 页面级或区域级视觉检索。

对每条路线说明输入、索引对象、召回证据、适用条件、失败模式、权限和验收，不写固定优劣排序。

#### 现有六段诊断

- 解析。
- 索引。
- 召回。
- 重排。
- 上下文组装。
- 生成与引用。

当前已经具备六段诊断、检索侧与生成侧责任。默认不重复新增。只有教学取用仍有明显缺口时，才把既有内容重组为“症状 → 观测 → 假设 → 定位动作 → 修复 → 复验”，不能用一个总准确率掩盖失败位置。

不采用通用相似度阈值、GraphRAG 成本倍数或 Text-to-SQL 固定正确率。

### 8.2 Multimodal

主 owner：multimodal。

补充 Barge-in 状态与取消语义：

1. 检测用户打断。
2. 停止当前播放。
3. 取消或隔离旧生成任务。
4. 丢弃到达过晚的失效输出。
5. 确认已经被用户听到或看到的边界。
6. 恢复正确上下文状态。
7. 生成新的响应。
8. 记录取消、延迟和状态证据。

连接现有 VAD、WebRTC/SIP、级联与端到端路线、延迟预算和验收内容。不加入当期厂商型号、价格或“默认最佳”延迟。

### 8.3 MCP

主 owner：mcp。

先运行重复检查。当前协议版本、对象、状态、身份和终态边界已经较深，只有教学增益明确时才补：

- 初始化与能力协商。
- 工具发现。
- 工具调用与结果。
- 错误、取消和超时。
- 身份和授权边界。

使用最小真实报文逐层注释，所有字段必须对应当前官方规范。若只是把已有文字换成代码框，不实施本项。

## 9. 单批执行流程

每批严格按顺序：

### 9.1 基线冻结

- 运行 npm run module:polish -- status。
- 新批次在状态允许时运行 `npm run module:polish -- prepare next`；恢复已有批次则按原批次 ID 继续。
- 记录 HEAD、计划摘要和关键文件摘要。
- 检查无关改动与前一批 receipt。

### 9.2 并行只读研究

最多三个工作包：

- 机制、失败与边界。
- 当前覆盖、重复项和模块 owner。
- 证据、术语、问答和文件影响。

### 9.3 证据门

- 目标库只作线索。
- 关键机制回到官方、标准或论文。
- 数字说明条件和不可外推边界。
- 动态内容分流到第 3 阶段或 Claim。
- 研究改变候选范围、owner、目标合同或高风险结论时暂停，回到候选裁决，不在写入批次中扩展。

### 9.4 单写者整合

- 先写回明确 owner，不增加第五层 expansion 文件。
- 共享内容只修改一次。
- 同步正文、课程、实战、问答、证据和 Reference 的实际受影响部分。
- 图、表、卡和问答按知识需要决定数量。

### 9.5 独立中文审查

- 机制是否成立。
- 是否与现有内容重复或冲突。
- 是否出现无来源数字和绝对承诺。
- owner 与相关模块边界是否清楚。
- 问答是否有独立客户决策价值。

### 9.6 定向与全量验证

- 模块内容与来源解析。
- 问答重复和高词面重合。
- 路由、锚点、知识视图和移动端。
- 中文单线发布契约。
- 完整 npm run check。

### 9.7 用户 Review

每批交付内容差异、来源、拒绝项、测试和页面检查结果。用户确认后才进入下一批。

## 12. 中文单线发布依赖

中文正文变化会使现有双语内容哈希失效；新增问答或证据卡还会打破数量和证据关系对齐。共享 updatedAt 也会让未同步英文页显示中文最新日期。

因此不得：

- 关闭 test:bilingual。
- 为未审校英文重新生成 PASS 记录。
- 修改英文占位文案假装同步。
- 让英文页显示中文最新日期。

必须先实施并验证 `07-CHINESE-ONLY-DELIVERY-CONTRACT.md`。固定顺序：

1. 冻结最后真实双语基线、英文 authored 哈希、英文有效内容哈希和对象清单。
2. 实现并验证永久语言日期、延期状态和对象级差异校验。
3. 在写中文前建立模块延期记录及计划 affected objects。
4. 实施中文变化并按规则刷新中文日期。
5. 验证实际中文差异完全落入批准范围和登记对象。
6. 验证英文 authored 内容、英文有效内容和英文日期保持原样。
7. 未登记差异、英文有效内容变化或无效 receipt 立即阻断。

为减少未来同步成本，本阶段默认优先改写现有中文对象。只有产生独立客户决策价值、结构延期能力已经通过且英文运行时不存在未解耦依赖时，才新增或重排问答与证据。

## 14. 完成标准

- 所有新增内容来自已确认差异矩阵。
- 每项内容有唯一主 owner。
- 每项内容支持明确客户判断。
- 机制、失败、边界、控制和证据完整。
- 不包含现成厂商排名、价格或固定经验阈值。
- 正文、问答、证据和 Reference 没有漂移。
- 不新增第五层作者补丁。
- No-op 项未触发日期、延期或正式内容变化。
- 实际变化未超过 `approvedScope`。
- 英文 authored 内容与英文有效内容均未改变。
- 中文单线延期契约有效，英文显示真实 `DEFERRED/NOT_ALIGNED`，没有虚假 PASS 或日期误报。
- 所有定向检查和 npm run check 通过。
- 用户逐批确认完成。

如果本阶段产生经用户确认的内容变更，只在 `codex/ai-knowledge-base-content-improvement` 形成经验证的本地批次检查点和 seal receipt；不合并 `main`、不推送、不发布。全部候选 no-op 或仅研究时只保存回执。最终发布统一遵守总体计划的分支合并门。

## 15. 停止与回退条件

以下任一发生即暂停：

- HEAD、远端、seal、Stage 0 矩阵哈希或路由包哈希漂移。
- 候选未批准、owner 未解决、`approvedScope` 不清或出现范围外内容。
- 新证据改变候选判断、目标合同或风险等级。
- `localeGate` 失败、延期未登记、对象差异超范围或英文有效内容变化。
- 发现需要新模块、路由或系统性共享规则。
- 定向检查或 `npm run check` 失败。

新知识缺口退回 Stage 0；中国动态或高风险问题路由 Stage 3；共享运行时与语言契约问题退回 07；不得在当前批次临时扩展。
