# 第 4 阶段：跨行业迁移验证计划

状态：`in-review`

## 1. 阶段目标

验证前述通用方法能否迁移到一个真实高风险行业场景，形成可复用的跨模块蓝图。

本阶段不建设行业百科，不在第一轮增加新模块，也不追求多个行业案例数量。

## 2. 进入条件

- 第 3 阶段完成并通过高风险审查。
- 当前分支为 `codex/ai-knowledge-base-content-improvement`。
- 相关 Claims 与 References 在有效期内。
- Stage 0 行业候选、Stage 3 receipt、用户确认的行业、业务场景和 AI 禁止动作均已就绪。
- 业务、合规、Security、Evaluation 和 Operations 的 Review 责任明确。
- 缺少行业专家时，案例明确标记为教学蓝图，不伪装成生产标准。
- 中文单线发布契约持续有效，相关候选有有效 `localeGateReceipt`。

## 3. 建议试点

建议首选：

> 跨地区保险理赔材料受理与初审助手。

AI 只负责材料接收、质量检查、事实与证据提取、缺件提示和初审建议；不得自动核赔、定损、拒赔、确定资格、决定金额或发起付款。

选择理由：

- 当前 Model Landscape、RAG、Multimodal、Agent、Governance、Security 已有分散的保险理赔示例。
- 可以同时验证文档与图片、授权检索、引用、工具调用、人工决策、申诉和恢复。
- AI 允许和禁止动作可以清楚限定。
- 比新建一个完全陌生行业叙事更能检验现有知识的迁移性。

备选：

- 工业现场巡检材料助手，法规负担较低。
- 金融审批、公共服务或医疗支持，只有具备足够法源和专业 Review 时再选择。

最终试点必须由用户在 4A 前确认。在用户未另行选择时，本计划保留保险理赔材料受理与初审助手作为推荐默认，但“写入计划”不等于行业场景已经批准。

## 4. 明确边界

- 不把初审助手描述为自动核赔或自动赔付。
- 不发布行业时限、阈值、责任或法规结论，除非有官方法源和专业审查。
- 不把客户流程、内部 SLA 或经验泛化成行业标准。
- 不新建保险 AI 模块或路由。
- 不在多个模块重复完整案例。
- 不扩展第二个公开行业案例。
- 不修改英文内容。

## 5. 场景合同

正式研究前冻结：

- `scenarioId`、版本、内容哈希和批准日期。
- `validationMode`：`teaching-blueprint` 或 `production-guidance`。
- 业务结果和现有人工基线。
- 精确地域、用户、服务对象和业务责任主体。
- 材料、图片、保单、规则和业务记录的权威来源。
- AI 是辅助、建议还是自动执行。
- 明确禁止由模型作出的决定。
- 权威业务系统、最终决定 owner 和写入权限。
- 数据分类、权限、地域、是否使用真实客户数据和保留要求。
- 成功指标、伤害指标和停止条件。
- 人工接管、申诉和事件路径。
- 上线、变更、回滚和退出责任。

没有场景合同，不得开始跨模块写作。

行业、地域、禁止动作、最终决定 owner 或 `validationMode` 发生变化时，已有 4A/4B receipt 失效，必须重新审计，不能直接替换场景。

## 6. 单一主蓝图

完整蓝图只放在 Solution Patterns，其他模块只维护各自主责机制并通过“相关模块”连接。

建议流程：

1. 材料接收与身份、授权检查。
2. 文件质量、完整性、来源和溯源检查。
3. 从授权权威源检索保单、条款和业务记录。
4. 提取事实、证据位置、不确定性和缺件。
5. 生成带引用的初审建议。
6. 由授权人工或确定性规则决定资格、责任、金额和付款。
7. 写入权威业务系统并通知客户。
8. 支持纠正、申诉、事件处置和重新评估。
9. 支持模型、供应商或流程退出。

每一步定义：

- 输入和权威来源。
- AI 允许动作。
- AI 禁止动作。
- 人工或系统 owner。
- 必须保留的证据。
- 失败、降级和恢复。
- 指标与上线门。

## 7. 模块责任

| 模块 | 唯一主责 |
| --- | --- |
| Solution Patterns | 业务结果、基线、范围、闭环、交付和退出 |
| Data Engineering | 权威来源、数据合同、血缘、同步和删除传播 |
| Multimodal | 扫描件、照片、表格的质量、解析、溯源和定位 |
| RAG | 授权检索、引用、拒答和状态新鲜度 |
| AI Agent | 有界工具调用、幂等、未知结果和补偿 |
| Security | 注入、越权、跨客户泄漏、工具滥用、隔离和恢复 |
| AI Governance | 风险分级、审批、责任、监督、申诉和复核 |
| Evaluation | 分对象和生命周期评测、硬门、人工复核和重复试验 |
| AI Ops | 发布、监控、变更、事件、恢复和回滚证据 |
| Model Landscape | 模型、区域、版本候选、试点和退出 |

其他模块不能复制完整故事，只能引用主蓝图并解释自身责任。

## 8. 行业内容分层

每项内容必须标记：

| 类型 | 含义 |
| --- | --- |
| stable | 跨行业稳定方法，可进入通用正文 |
| parameterized | 方法稳定，阈值、角色或证据由客户配置 |
| industry-specific | 依赖保险法规或行业规则，需官方法源和专业 Review |
| blocked | 证据或责任不清，暂不公开 |

这层标记防止单一保险实践被误写成通用最佳实践。

## 9. 来源与 Claim 分流

- 行业研究完整继承 Stage 3 的场景冻结、官方来源优先、法源摘录、结论映射、冲突和高风险审查协议。
- 通用架构、威胁模型和责任边界不建 Claim。
- 行业法规状态、生效日期、法定期限和适用范围使用官方法源和原子 Claim。
- 客户规则、内部时限、审批阈值和理赔政策不进入公共 Claim。
- 统计数字、行业平均值和产品性能必须单独核验，不能替代客户基线。
- 目标库行业材料只用于发现问题，不作为正式证据。
- 无法确认的行业结论保持 Review 问题或 hold。

没有合格行业专家时，只能发布经过验证的 `stable` 与必要的 `parameterized` 教学方法；`industry-specific` 生产结论保持 blocked。高风险发现统一记录 finding ID、严重度、影响对象、reviewer、owner、支撑证据、处置和复核日期。

## 10. 第 4A 批：只读迁移审计

并行只读检查现有案例和模块，输出：

- 当前保险相关内容清单。
- 重复、冲突和空白。
- stable、parameterized、industry-specific、blocked 分类。
- 每项控制的唯一 owner。
- 拟修改文件和明确不修改文件。

本批不写公开内容。

4A 开始前必须完成场景合同用户确认；只读审计结果改变行业、地域、AI 禁止动作或 validation mode 时，重新提交场景合同 Review。

## 11. 第 4B 批：主蓝图整合

最多三个模块：

- Solution Patterns。
- AI Governance。
- Security。

交付：

- 业务主蓝图。
- AI 允许与禁止动作。
- 责任与审批。
- 威胁路径。
- 申诉、事件、人工接管和退出。

## 12. 第 4C 批：必要证据与运行补齐

只有 4B 证明存在净新增缺口时，最多处理：

- Data Engineering。
- Evaluation。
- AI Ops。

Model Landscape、Multimodal、RAG 和 Agent 默认复用已有内容与关系。主责控制确实缺失时另提工作包，不顺带重写。

每批生成统一 receipt，记录 Stage 0 候选、Stage 3 输入 receipt、场景版本与哈希、批准范围、受影响对象、来源与 Claim、locale 影响、测试、风险发现和开放问题。只有当前 receipt 与冻结场景合同一致时，下一批才可启动。

## 13. 场景验收集

至少覆盖：

- 正常完整材料。
- 缺件和证据矛盾。
- 低质量扫描件或图片。
- 未授权或跨客户检索。
- 文档提示注入。
- 工具超时和执行结果未知。
- 模型、端点或版本变化。
- 人工与模型意见不一致。
- 客户纠正或申诉。
- 删除、撤回和记录传播。
- 安全事件、降级和恢复。
- 供应商或模型退出。

每项测试明确输入、预期状态、禁止副作用、证据产物和恢复路径。

## 14. 泛化验证

正式发布前，把 stable 控制只读套用到工业巡检影子场景：

- 无需修改即可成立，说明控制具有迁移性。
- 必须依赖保险术语或规则才能成立，应降级为 industry-specific。
- 影子场景只用于验证，不创建第二个公开蓝图。

## 16. 蓝图门禁

- 只有一个稳定蓝图 ID 和一个主责模块。
- 所有模块对 AI 角色和禁止动作表述一致。
- 资格、责任、金额和付款由授权人工或确定性业务系统决定。
- 每项控制有唯一 owner、证据产物和失效处理。
- 数据权威源、业务终态和系统记录跨模块一致。
- 行业事实通过官方法源和专业审查。
- 动态事实进入 Claim，不散落日期、产品状态或阈值。
- 页面只使用“相关模块”，不引入第二注册表。
- 问答、证据、Reference 和中文更新时间同步。
- 不新增模块、路由或英文内容。
- 定向检查和 npm run check 通过。

## 17. 阶段交付物

1. 经用户确认的行业场景合同。
2. 单一主责的跨模块蓝图。
3. AI 允许和禁止动作。
4. 数据、威胁、治理、评测、运行和退出证据链。
5. 官方法源与 Claim 分流。
6. 高风险人工审查记录。
7. 场景验收集。
8. 工业巡检影子迁移结果。
9. 中文单线延期记录。
10. 全量门禁报告。
11. 4A～4C receipt 与未实施、no-op、hold 清单。
12. 面向 Stage 5 的最终蓝图 ID、场景哈希、风险和发布范围交接包。

## 18. 完成标准

- 行业与场景边界经用户确认。
- 主蓝图只出现一次。
- 模块 owner 无冲突。
- AI 禁止动作在所有模块一致。
- 高风险结论有官方法源和专业 Review。
- stable 与 industry-specific 明确分开。
- 动态事实进入 Claim。
- 影子场景验证完成。
- 英文内容未修改。
- 定向检查和 npm run check 通过。
- 英文 authored 内容、有效内容和真实日期均保持冻结基线。

如果本阶段产生经用户确认的内容变更，只在 `codex/ai-knowledge-base-content-improvement` 形成经验证的本地批次检查点和 receipt；不合并 `main`、不推送、不发布。只读迁移审计或全部 no-op 时只保存回执。最终发布统一遵守总体计划的分支合并门。

## 19. 停止条件与 Stage 5 交接

以下任一发生即暂停：

- HEAD、远端、seal、场景哈希或关键文件摘要漂移。
- 场景合同、地域、最终决定 owner、AI 禁止动作或 validation mode 改变。
- 行业来源状态冲突、Claim 过期或 high/critical 风险未解决。
- 必要专家不可用，但拟写内容仍包含 industry-specific 生产结论。
- locale gate 失败、延期遗漏或英文有效内容变化。
- 新缺口需要增加模块、路由或跨阶段共享规则。
- 定向检查或 `npm run check` 失败。

Stage 5 只接收有效 receipt、冻结场景合同、唯一蓝图 ID、已解决风险、明确 hold 清单和最终受影响对象。行业或内容语义问题返回 Stage 3/4，不能在发布硬化阶段临时修补。

## 20. 明确不做

- 不构建行业百科。
- 不增加行业模块。
- 不自动化高影响最终决定。
- 不把客户内部规则公开化。
- 不扩展第二个公开行业。
- 不修改英文内容。
- 不运行 Portable 流程。
- 不在计划 Review 阶段开始正式研究或写入。
