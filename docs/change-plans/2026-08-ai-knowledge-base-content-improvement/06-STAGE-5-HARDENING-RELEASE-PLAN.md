# 第 5 阶段：内容硬化、验证与发布计划

状态：`in-review`

## 1. 阶段目标

把前四个阶段已经确认并实施的中文内容整理成一个证据完整、无重复、可构建、可回归的专项工作分支；经用户最终 Review 后，才合并为正式分支上的精确发布提交。

本阶段不再扩展新主题。发现新的内容缺口时回到对应阶段建立候选，不能在发布收尾中临时扩展范围。

## 2. 进入条件

- 第 0～4 阶段计划均已 Review。
- 本轮实际实施的每个内容批次都有用户确认和完成 receipt。
- 所有 Stage 0 候选都能归入 implemented、no-op、research-pending、deferred、rejected 或 hold。
- 未实施、拒绝、观察和 hold 条目有明确记录。
- 中文单线发布契约有效。
- 所有新增来源和 Claims 已完成核验。
- 工作区没有未归属或无关改动。
- 当前 HEAD、远端和上一批 seal 一致。
- Stage 1～4 的基线、范围、来源、Claim、风险和 locale receipt 均有效。
- 当前分支必须是 `codex/ai-knowledge-base-content-improvement`；`main` 在最终合并授权前保持未修改。

任一条件不满足，先恢复对应阶段，不开始发布硬化。

## 3. 冻结发布范围

建立一次最终变更清单：

- 受影响模块。
- 改写和新增的中文章节、问题、证据卡和实战。
- 新增或更新的 sourceId。
- 新增、替换、观察或失效的 claimId。
- 新增术语和知识关系。
- 首页、问题目录和学习路径变化。
- schema、检查和共享组件变化。
- 英文延期模块、稳定 ID 和最后有效英文快照。
- 明确未修改的范围。

此后不再接受未登记变更。发现遗漏时先更新清单并重新 Review。

Stage 0 路由到 Stage 5 的项目只能是已批准的发布硬化、回归或系统性质量规则，不能把 Stage 5 当成绕过 Stage 2～4 的新内容入口。

## 4. 内容硬化

### 4.1 绝对和伪精确表达

专项扫描：

- 唯一、永远、一定、完全、零风险。
- 80%、八成、大幅、显著等无来源量化。
- 固定成本倍数、利用率线和准确率门槛。
- 固定周数、卡数、样本量和办理周期。
- “使用某产品即可合规”。
- “事故一定由某一方负责”。

处理方式：

- 有可靠数据时补 scope、版本、日期、来源和边界。
- 只是经验时明确写成待验证假设。
- 无法支持时删除。

### 4.2 机制与边界

逐项确认：

- 定义、输入输出、机制和状态完整。
- 失败模式与控制对应。
- 技术状态和业务终态分开。
- 权限、责任和人工接管清楚。
- 不能外推的条件明确。
- 结论强度不超过证据。

### 4.3 重复与 owner

- 检查同一道客户决策是否在多个模块重复。
- 检查完整行业或中国故事是否只在一个主模块出现。
- 相关模块只保留本层机制和稳定回链。
- 新内容写回真实 owner，不增加第五层 expansion 文件。
- 如果历史作者文件严重分散，只做本批必要聚合，不顺带重构无关内容。

### 4.4 读者语言

- 删除编辑、构建、维护和内部流程语言。
- 标题使用客观陈述或名词短语。
- 技术词首次出现用普通中文解释。
- 避免咨询式空话和重复句式。
- 现场话术保持自然，但不牺牲边界与证据。

### 4.5 硬化范围边界

Stage 5 可以修复不改变语义的拼写、格式、失效锚点、渲染和已批准规则执行问题。

以下发现必须退回原阶段重新建立候选和 Review，不能在收尾中直接修改：

- 删除或改写会改变判断、边界或答案。
- owner 调整导致内容迁移。
- 新来源、Claim、法规结论或行业事实。
- 新 schema、等级映射或读者可见命名变化。
- 新模块、路由或跨阶段范围。

## 5. Reference 与 Claim 硬化

### 5.1 Reference

- 所有 URL 只在 app/reference-content.mjs 维护。
- sourceId 稳定且不重复。
- 标题、发布方、证据类型、说明、边界和 verifiedAt 完整。
- 每个来源进入至少一个模块分组。
- 模块、问答、证据卡、课程和实战只引用稳定 sourceId。
- 用户能从公开 Reference 页面直接打开权威原文。

### 5.2 Claim

- 动态事实拆成最小原子 Claim。
- status、grade、cadence、sourceIds、scope、boundary 和复核日期有效。
- announcement、watch、replaced 和 active 状态正确。
- 发布候选中没有过期、C 级或范围不明的确定性卖点。
- 产品、价格、法规状态和版本不散落到永久正文。
- 已替代 Claim 不再被页面引用。

### 5.3 等级语义

当前公开来源和内部 Claim 使用不同等级体系。本阶段检查文档和界面是否混称为同一 evidence grade。若修复需要新增映射说明、读者可见改名或改变历史证据含义，阻止发布并退回对应内容或契约阶段；只有已预先批准的非语义修正才能在本阶段处理。

## 6. 内容契约同步

按实际变更检查：

- app/module-publication.mjs。
- app/module-content-registry.mjs 及真实内容 owner。
- 问答、深答、下一问、basis 和 evidence。
- 证据卡。
- 课程和学习任务。
- app/reference-content.mjs。
- knowledge/claims/index.json。
- app/terminology.mjs。
- 知识关系和相关模块。
- 首页路径和问题现场层。
- 中文与英文延期契约。
- 自动检查和质量追溯矩阵。

不要求每类对象都发生修改；要求所有真实影响都有检查结论。

## 7. 日期门禁

- 模块事实、机制、边界、判断或回答发生实质变化时，刷新中文 updatedAt。
- 每个模块只在页顶或页底显示一次最近更新时间。
- 课程、深挖、实战和证据卡不显示逐条日期。
- 只有整道新增问题设置 addedAt。
- 改写既有问题不刷新 addedAt。
- 客户口语、意图分类、现场层级和纯路径调整不刷新模块日期。
- 纯排版、样式或格式不刷新日期。
- 英文页面使用最后真实英文同步日期，不显示中文最新日期。

中文和英文日期隔离的技术契约见 07-CHINESE-ONLY-DELIVERY-CONTRACT.md。

## 8. 自动验证分层

### 8.1 变更对象定向检查

根据实际改动运行：

- 现场元数据、搜索和路径检查。
- 模块内容与 owner 解析。
- 问答规范化重复和高词面重合。
- sourceId、Reference 分组和新鲜度。
- Claim schema、状态和复核周期。
- 术语和知识关系。
- 日期策略。
- 中文单线英文延期契约。

### 8.2 模块批次门禁

- npm run module:polish:validate。
- 核验批次、依赖、进度和 seal。
- 确认上一批完成后才封存下一批。

### 8.3 全量门禁

必须运行：

- npm run lint。
- npm test。
- npm run check。

npm run check 已包含构建、模块打磨验证、双语回归、生产 HTML、问答重复和代码检查。不得用中文单线为理由跳过它；应通过正式延期契约让检查真实反映当前状态。

日常发布不运行：

- npm run portable:check。
- kb:doctor。
- kb:validate。
- handoff 审计。
- portable 测试。

只有用户另行明确要求 portable、离线 ZIP 或跨机器交接时才加入。

## 9. 人工页面 Review

### 9.1 中文重点页面

- 首页。
- /questions。
- 所有受影响模块。
- /references。
- /glossary。
- /knowledge-graph，如关系发生变化。

### 9.2 设备与交互

检查：

- 1440×900 与 1366×768 桌面。
- 平板宽度。
- 390px 左右手机。
- 键盘导航、可见焦点和筛选。
- 无结果、展开、锚点、返回和 URL 恢复。
- 长表格、代码、机制图和中文换行。
- 全局横向溢出和遮挡。

### 9.3 英文回归

只做技术回归，不审校内容：

- /en、/en/questions 和受影响模块对应英文页可构建。
- 英文 authored 内容文件摘要和英文有效内容哈希均未变化。
- 中文元数据和样式未泄漏到英文页。
- 英文显示最后真实同步日期。
- 英文旧内容明确处于已登记延期状态，不生成虚假 PASS。

## 10. 对抗式最终审查

至少安排三个只读视角：

1. 内容与重复：寻找旧结论、重复 owner、过度扩张和模板化。
2. 证据与动态性：寻找来源不支持、日期过期、Claim 漏登记和边界不足。
3. 安全、法律与责任：寻找主体错误、绝对归责、自动化越界和专业复核缺失。

主 Agent 对所有发现逐条裁决。未解决的高风险问题阻止发布。

## 11. Git 范围确认

最终分支 Review 前：

- 当前分支是 `codex/ai-knowledge-base-content-improvement`。
- git status 显示的每个文件都属于本计划。
- 检查无私有 inbox、原始聊天、临时文件、构建产物或外部仓库副本。
- 检查计划文档与正式内容的状态一致。
- git diff --check 通过。
- 冻结 `merge-base(main, feature)`，检查 `main` 是否在实施期间漂移。
- 向用户交付 `main...codex/ai-knowledge-base-content-improvement` 的完整 diff、提交列表、变更统计、风险和延期摘要。
- 不自动 stash、reset、覆盖或纳入无关改动。

如果存在用户其他改动、`main` 漂移或合并冲突且不能安全隔离，暂停并说明；不得自动 rebase、覆盖或裁决冲突。

## 12. 提交与推送

固定顺序：

1. 在专项分支完成最终范围 Review、提交检查点并运行 `npm run check`。
2. 向用户交付专项分支相对 `main` 的完整合并包。
3. 用户亲自合并，或明确授权 Codex 把专项分支合并到 `main`；没有授权不得合并。
4. 合并前重新同步并核验 `main`。基线漂移或冲突必须重新 Review。
5. 合并后记录 `releaseCommit`；它必须是 `main` 上的合并提交或经确认的 fast-forward 提交。
6. 在合并后的 `main` 再次运行 `npm run check`，确认工作区没有范围外变化。
7. 推送前预检 Git 远端、Sites 发布能力和权限；无法执行 Sites 时不得先推送。
8. 推送 `releaseBranch=main`。
9. 查询远端引用，确认 `remoteSha === releaseCommit`。
10. 不在推送后继续修改发布候选。

计划、研究或未确认草稿本身不触发提交发布。

专项分支在最终授权前不推送。如果最终硬化没有产生任何正式文件变化，且公开站点已经对应通过验证的当前远端 `main`，不创建空提交；改为交付 no-op 验证 receipt。只要合并产生正式变化，就必须执行下面的完整 Sites 链路。

## 13. Sites 发布

推送成功后同一任务必须：

1. 运行 `npm run sites:release-check`。
2. 验证 release-check 候选提交等于 `releaseCommit`。
3. 使用 Sites 发布工作流部署该精确候选。
4. 记录 `sitesVersionId`、`sitesSourceCommit` 和上一个公开版本 ID。
5. 轮询到发布成功，并确认 `sitesSourceCommit === releaseCommit`。
6. 打开正式地址：
   https://cloud-ai-presales-fieldbook.lijx.chatgpt.site
7. 检查首页、问题页、受影响模块和 Reference。

推送后如果需要修改任何 tracked 内容，旧提交立即失去候选资格；必须创建新提交，并从检查、推送、release-check 和 Sites 全部重跑。只有部署瞬时失败且内容不变时，才可重试同一提交。

如果 Git 推送成功但 Sites 失败：

- 任务保持未完成。
- 报告失败步骤、提交 SHA 和当前公开版本。
- 保持仓库可恢复状态。
- 修复发布或从同一提交重试，不临时加入新内容。

发布成功但公开烟测失败时同样保持未完成；内容修复必须形成新提交并重新走完整发布链。

## 14. 发布交付物

1. 最终范围清单。
2. 各阶段 implemented、no-op、deferred、rejected 结果。
3. 中文内容与文件摘要。
4. Reference 与 Claim 变化。
5. 模块与问题日期变化。
6. 英文延期清单和最后同步状态。
7. 自动检查结果。
8. 人工页面 Review 结果。
9. Git 提交和远端一致性。
10. Sites 发布结果和公开地址。
11. 未实施候选与后续建议。
12. Release receipt，至少保存：
    - `releaseCommit`、`releaseBranch`、`remoteRef` 和 `remoteSha`。
    - release-check 结果。
    - `sitesVersionId`、`sitesSourceCommit` 和上一个公开版本 ID。
    - 公开 URL、发布时间和烟测结果。

## 15. 完成标准

- 所有正式变更经过用户确认。
- 没有范围外改动。
- 内容、问答、证据、Reference、Claim、术语和路径一致。
- 无无来源数字、绝对承诺或过期确定性事实。
- 高风险结论有官方来源和人工 Review。
- 中文日期正确，英文日期不误报。
- 英文 authored 内容与英文有效内容都等于冻结基线，延期状态真实。
- npm run check 通过。
- 本地与远端 SHA 一致。
- Sites 使用同一提交发布成功。
- 正式地址已经打开验证。
- Release receipt 完整且引用的提交、远端和 Sites 版本一致。

## 16. 停止与回退条件

以下任一发生即暂停：

- HEAD、远端、seal、范围哈希、receipt 或关键文件摘要漂移。
- 最终授权前当前分支不是专项工作分支，或 `main` 被意外修改。
- `main` 基线漂移、合并冲突或合并结果超出用户批准范围。
- 工作区存在未归属或与用户无关的改动。
- 来源、Claim、风险、locale gate 或延期状态失效。
- 硬化发现需要新的语义内容、schema、模块或跨阶段规则。
- 定向检查或 `npm run check` 失败。
- `releaseCommit` 形成后工作区出现 tracked 修改。
- 远端 SHA、release-check 候选或 Sites source commit 不一致。
- Git 推送后 Sites 发布或公开烟测未成功。

新知识缺口回 Stage 0/2/3；行业场景和禁止动作变化回 Stage 4A；发布技术失败留在 Stage 5。内容修复必须形成新的候选或批准范围，不能把发布失败当成扩大内容范围的授权。

## 17. 明确不做

- 不在收尾阶段增加新主题。
- 不修改英文内容。
- 不跳过或删除失败测试。
- 不为通过门禁生成虚假英文 Review。
- 不纳入私有 inbox、原始聊天或临时文件。
- 不运行无关 Portable 流程。
- 不只推 GitHub 而不发布 Sites。
- 不在 Sites 失败时标记完成。
