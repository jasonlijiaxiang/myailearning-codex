# 总体提升计划

状态：`approved-for-execution`（2026-08-05 用户指示全量自主执行，见 DECISIONS.md D-012）

## 1. 背景与结论

本计划基于对 `jasonlijiaxiang/ai-knowledge-base` 和当前 Cloud × AI 售前知识库的只读审计。

两个知识库在主题上高度重叠，但优势不同：

- 当前库更强在 Web 原生结构、稳定内容 ID、集中 References、Claim 生命周期、术语关系、机制—判断—边界表达、AI Governance、Predictive AI/MLOps 和内容门禁。
- 对照库更强在中国交付面、国内平台与生态、现场备战、时间预算学习路径、客户口语、诊断式教学和售前交付方法。

因此，本次工作的方向不是迁移或合并两个仓库，而是：

> 保留当前库作为唯一正式知识系统，只吸收对照库中经过去重、重新核验且能提升客户决策价值的净新增内容。

## 2. 本轮范围

### 包含

- 对照库内容差异矩阵。
- 中文现场核心问题和时间预算学习入口。
- 稳定的方案方法、诊断方法和 Agent/Evaluation 增量。
- 中国 AI 合规、国内模型与 MaaS、多模态交付专项研究。
- 一个高风险行业的迁移验证。
- 中文内容硬化、全量门禁和公开发布。

### 不包含

- 英文内容同步、翻译或审校。
- 整章复制对照库内容。
- 新建第二套问题库、来源台账或模块目录。
- 引入 PPT 与网页双内容源。
- 直接复制价格、排名、份额、版本、产品能力和经验阈值。
- 日常任务中的 portable 审计、离线 ZIP 或跨机器交接。

## 3. 全局内容原则

1. 对照库是发现与 provenance 线索，不是最终事实来源。
2. 候选内容以“能改变一个客户判断的知识单元”为粒度，不按整章搬运。
3. 每项正式知识内容必须有明确主模块 owner；全局入口、问题目录和共享质量规则必须有明确全局或共享 owner。
4. 稳定机制留在正文，动态事实进入 Claim 生命周期。
5. 法规、安全、责任和产品结论必须写明适用范围与不可外推边界。
6. 新内容仍须形成“定义 → 机制 → 边界 → 判断 → 证据”的完整链路。
7. 问题数量、卡片数量和图表数量不是目标；取用效率和决策质量才是目标。
8. 首页只维护全局入口、知识地图和学习路径，模块正文继续留在独立模块地址。
9. 正式来源 URL、证据类别、边界和核验日期继续只在集中 Reference 契约维护。

## 5. 第 0 阶段：内容差异矩阵

本阶段只做研究决策，不修改正式内容。

核心工作：

- 建立输入覆盖账，按 occurrence 提取后归并为 canonical candidate。
- 从目标库提取稳定机制、客户问题、诊断方式、交付方法、中国生态线索、动态事实和教学结构。
- 与当前模块、问答、深挖块、课程、术语、References 和 Claims 逐项去重。
- 排除目标库从当前库旧版本吸收后形成的循环回流内容。
- 判断客户决策价值、证据准备度、时效风险和模块归属。
- 将每项候选分为吸收、重新研究、只借表达、观察或拒绝。
- 将研究建议与用户最终裁决分开，并生成 Stage 1 取用投影和 Stage 2～5 机器路由包。

详细设计见 `01-STAGE-0-GAP-MATRIX-PLAN.md`。

## 6. 第 1 阶段：中文现场备战层与学习路径

目标是让现有 21 个模块和 320 道正式问答更容易在会前、现场和会后取用，不建立第二份答案内容源。

计划内容：

- 在现有细粒度标签之上增加稳定的跨模块问题意图，例如概念、选型、架构、成本、安全、评估、运营、治理。
- 为高频问题补充客户常用口语别名，只用于搜索和发现。
- 从现有问题中精选现场核心集，直接使用正式 `shortAnswer`；需要改写的题交给第 2 阶段，不新建重复答案字段。
- 设计信息不足、动态事实、法律安全和责任问题的兜底话术。
- 增加 10 分钟、30 分钟、2 小时和系统学习四种时间预算路径。
- 检查当前未进入首页场景路径的正式模块，并为真正独立的学习目标补充入口。

本阶段只处理中文；英文页面保持原状并通过兼容性回归。

本阶段只增加最小稳定入口和客户别名投影，不顺带重构全站搜索算法、模糊搜索或完整可分享筛选状态。

## 7. 第 2 阶段：稳定内容补强

按模块复杂度、共享文件冲突和审查能力划分小批次，不设数字硬上限。

### 第 2A 批：方案与交付诊断

- Solution Patterns：在现有 PoC、单位经济和退出基础上，复核客户参与责任与资产交接；已有内容不重复建设。
- Data Engineering：把现有来源、身份、连接器、权限和删除内容整理为会前数据就绪分诊和 PoC 缩围。
- AI Infra Compute：把现有工作负载、设施、网络存储和采购边界前置为设施与供给就绪门。

### 第 2B 批：Agent 与 Evaluation

- AI Agent：现有 Sub-agent 内容默认 no-op；真正候选是低代码与 Code-first 决策维度和 Memory Poisoning。
- Evaluation：Benchmark Atlas，明确每类基准测什么、不能证明什么以及如何与客户任务终审衔接。

### 第 2C 批：RAG、Multimodal 与 MCP

- RAG：现有诊断链默认 no-op；候选是多模态检索路线的决策级比较。
- Multimodal：Barge-in 的停止播放、取消旧生成、丢弃失效输出和恢复上下文状态。
- MCP：当前协议内容默认 no-op；只有确认存在教学缺口时，补版本化最小真实报文。

本阶段不吸收实时榜单、平台价格、无条件性能倍数或固定生产阈值。

## 8. 第 3 阶段：中国交付专项

### 第 3A 批：中国 AI 合规分诊

主要落在 AI Governance 与 Security：

- 服务受众、主体角色、部署方式、模型来源和数据流分诊。
- 内容生成、推荐、决策支持和自动执行的不同责任面。
- 个人信息、重要数据、敏感行业数据和跨境触发点。
- 内容标识、备案、登记、日志、申诉、人工复核和事件处理。
- 法律复核触发条件和上线证据包。

所有具体义务必须在执行时从官方法源重新核验，公开内容明确为知识分诊而非法律意见。

### 第 3B 批：国内模型与 MaaS 决策面

主要落在 Model Landscape：

- 地域、API/托管/专属实例/私有化交付模式。
- 模型目录、版本治理、企业采购、数据与日志政策。
- 配额、服务承诺、评估、回滚、多模型路由和退出能力。
- 平台名称、价格、版本和地区状态进入 Claim，不进入稳定课程骨架。

### 第 3C 批：多模态内容交付链

主要落在 Multimodal、Solution Patterns，并关联 Security/Governance：

- 素材授权、内容审核、生成标识、发布与分发。
- 日志证据、内容撤回和事故处置。
- 质量、延迟、成本和安全验收。

## 9. 第 4 阶段：跨行业迁移验证

选择一个高风险行业试点。当前建议优先使用“跨地区保险理赔材料受理与初审助手”，因为现有多个模块已经有分散的理赔例子，且可以清楚限定 AI 不得自动核赔、拒赔、决定金额或付款。最终场景仍由用户 Review 确认。

工作内容：

- 建立业务结果、AI 角色、禁止自动化边界、数据分类、责任主体、成功与伤害指标、人工接管和事故流程的场景合同。
- 将场景映射到 Solution Patterns、Data Engineering、Security、AI Governance、Evaluation、AI Ops 和 Model Landscape。
- 区分跨行业稳定原则、行业专属约束和需要专家确认的内容。
- 默认作为 Solution Patterns 的纵向蓝图，不轻易新增顶层模块。

## 10. 第 5 阶段：硬化、验证与发布

### 内容硬化

- 扫描“唯一、永远、一定、80%”等绝对或伪精确表达。
- 清除无来源数字、固定经验阈值和过度简化的法律安全结论。
- 检查动态事实是否误入稳定正文。
- 检查模块间重复、旧口径冲突和内容 owner。

### 契约同步

- 正文、问答、深度回答、下一步追问、证据卡、Reference、Claim、术语、知识关系和测试按实际变更同步。
- 模块发生事实、机制、边界或判断的实质变化时刷新中文模块 `updatedAt`。
- 只有整道新增问题设置 `addedAt`；改写、别名或分类调整不刷新原问题 `addedAt`。
- 不修改英文内容；只确保共享结构兼容、英文路由不坏且不误报同步日期。

### 发布

只有经用户确认的正式内容变更才进入：

1. 定向检查。
2. `npm run check`。
3. Git 范围确认、提交和推送。
4. 远端提交一致性确认。
5. `npm run sites:release-check`。
6. 使用同一提交发布 Sites 并轮询到成功。
7. 打开并交付正式公开地址。

如果 Git 推送成功但 Sites 发布失败，任务不得标记完成。

## 11. 语言范围

本轮中文单线迭代：

- 不修改 `app/i18n/en/**`。
- 不做英文写作、翻译、专业审校和内容一致性验收。
- 差异矩阵只记录未来英文同步涉及的稳定 ID、对象级中文差异和关闭条件。
- 共享 schema 和渲染逻辑必须对现有英文数据向后兼容。
- 英文模块 authored 内容、英文模块页实际解析出的 effective 内容和英文真实日期必须保持最后有效基线；全局 `/en/questions` 只允许死锚与导航准确性修复，不视为英文模块同步。
- 英文内容后续使用新的中文基线进行独立写作、专业审校和发布。

中文语义内容会使现有双语 Review 哈希、对象结构或共享更新时间失效。正式写入第 2 阶段前，必须先批准并实现 `07-CHINESE-ONLY-DELIVERY-CONTRACT.md`，形成有效 locale gate receipt；不能关闭双语检查、生成虚假英文 PASS、忽略英文运行时共享依赖或让英文页显示中文最新日期。

## 12. 阶段确认机制

1. 第 0 阶段计划已经确认；根据用户最新指示，第 1～5 阶段与横向契约本轮一次性写全并联合 Review。
2. 全部计划定稿前不开始正式内容实施。
3. 历史实施未完成第 0 阶段逐单元 screening；现有矩阵保持 `incomplete/draft`，不得倒推为用户已逐组确认。已进入公开内容的改动改由当前代码、主来源、Claim、本地化登记和最终门禁独立复核。
4. Stage 1 依次通过分类范围、现场内容、页面路径和实施结果 Review。
5. Stage 2～4 每个小批次在研究前、写入前和整合后分别经过相应 Review；研究授权不等于写入或发布授权。
6. 本专项的阶段 1～4 Review 只形成独立分支检查点，不视为正式发布确认，不中途推送或发布。
7. 只有用户明确给出最终合并/发布确认，或明确要求某个中间阶段提前成为正式版本时，才进入完整 Git 与 Sites 发布闭环。
8. Stage 5 对全局状态再次硬化，并在精确合并提交发布前取得最终正式范围确认。

## 13. 跨阶段 receipt 与停止规则

Stage 1～5 的每个批次统一记录：

- `stageId`、`batchId`、基线 SHA、范围哈希和关键文件摘要。
- 输入候选、前置 receipt、批准范围和实际结果。
- `sourceIds`、`claimIds`、受影响内容 ID 和日期影响。
- Locale requirement、延期记录与 gate receipt。
- 测试命令、结果、风险发现、owner、处置和开放问题。
- 用户 Review 的类型和日期。

统一停止条件：

- HEAD、远端、seal、范围或关键文件摘要漂移。
- 未批准候选、owner 冲突或范围外内容。
- 官方来源状态冲突、Claim 过期或 high/critical 风险未解决。
- 场景合同变化。
- Locale gate 失败、延期遗漏或英文有效内容变化。
- 定向检查或 `npm run check` 失败。
- Git 推送后 Sites 未成功。

新知识回到 Stage 0/2/3，中国适用性回到 Stage 3，行业场景变化回到 Stage 4A，纯发布技术故障留在 Stage 5；后续阶段不能替代前置阶段的内容裁决。

## 14. Git 分支隔离与最终合并契约

### 14.1 固定分支

- 正式基线分支：`main`。
- 本专项工作分支：`codex/ai-knowledge-base-content-improvement`。
- 分支创建基线：`671072cae7bb3ffcde366713eb421e65c2e9cbc1`。
- 本次计划、Stage 0 研究产物、Stage 1～5 实施、测试和 Review 留痕全部只在工作分支完成。
- 在用户最终确认前，不把工作分支合并到 `main`，也不直接修改正式分支。

### 14.2 中间检查点

- 计划、研究、no-op 和未确认草稿不自动提交。
- 经用户确认的阶段或批次可以在工作分支形成独立本地检查点提交和 seal receipt。
- 中间检查点不是正式发布确认，不推送、不部署 Sites。
- 默认不推送功能分支，因为本项目任何 Codex Git 推送都会触发公开 Sites 发布义务，与“最终完成后才进入正式版本”冲突。
- 如果未来确实需要远端备份、PR 或协作分支，必须由用户另行授权，并先重新确认 Git/Sites 发布边界。

### 14.3 最终合并门

只有同时满足以下条件，工作分支才进入最终合并 Review：

1. Stage 1～5 的实际代码结果与横向契约完成；Stage 0 明确保持 incomplete，且不再作为覆盖完整性、实施授权或合并质量证据。
2. 所有候选都有 implemented、no-op、deferred、rejected 或 hold 结果。
3. 所有定向检查和 `npm run check` 通过。
4. 工作分支没有范围外改动，所有 receipt 与 HEAD 一致。
5. 提供 `main...codex/ai-knowledge-base-content-improvement` 的完整差异、提交列表、风险和延期摘要。
6. 用户明确批准最终合并范围。

### 14.4 合并与正式发布

- Codex 不自行合并；只有用户亲自合并或明确授权 Codex 合并后，才更新 `main`。
- 合并前重新同步 `main`；基线漂移或冲突必须重新 Review，不能自动覆盖。
- 合并后的 `main` 提交是唯一正式发布候选；必须重新运行 `npm run check`。
- 检查通过后推送 `main`，确认远端 SHA，并用同一精确提交运行 `npm run sites:release-check` 和 Sites 发布。
- Git 推送成功但 Sites 未成功时，正式合并任务保持未完成。
- 工作分支只在合并、远端一致性和 Sites 发布全部成功且用户确认后删除，不自动清理。
