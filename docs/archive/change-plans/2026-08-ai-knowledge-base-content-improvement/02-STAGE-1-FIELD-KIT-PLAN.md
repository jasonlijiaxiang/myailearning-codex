# 第 1 阶段：中文现场备战层与学习路径计划

状态：`approved-for-execution`（2026-08-05 用户指示全量自主执行，见 DECISIONS.md D-012）

本阶段计划只有在第 0 阶段计划和差异矩阵完成 Review、且本阶段计划获得用户确认后才能执行。

## 1. 阶段目标

不增加第二套知识正文，把现有 21 个正式模块和 320 道正式客户问答组织成更适合会前准备、现场回答和会后跟进的中文取用层。

需要达到四个结果：

1. 用户能用客户自然说法搜到正确的正式问题。
2. 用户能按稳定的跨模块问题意图浏览，不再面对 262 个细碎标签。
3. 用户能快速找到经筛选的现场核心问题，答案仍来自正式问答。
4. 首页同时提供“按客户场景”和“按可用时间”两种全局学习入口。

本阶段只处理中文页面和中文取用元数据；不修改英文正文、英文问答或英文学习路径。

## 2. 当前状态与约束

### 2.1 问题目录

当前 /questions：

- 从 app/module-content-registry.mjs 派生全部正式问答。
- 服务端一次渲染全部 320 道问题。
- 每题展示短答、深答、下一问、题内证据和原模块入口。
- 支持关键词、模块和原始 tag 组合筛选。
- app/question-index.mjs 使用“模块 slug + 问题序号”作为目录键。
- 320 道问题共有 262 个细标签，其中 228 个只出现一次。

原始 tag 仍有模块内语义价值，但不适合继续作为全站主要分类。

### 2.2 首页路径

当前中文首页有四条场景路径：

1. 第一次与客户聊 AI 平台。
2. 设计企业知识助手。
3. AI 执行业务任务。
4. 规划私有化 AI 基础设施。

四条路径覆盖 15 个不同模块。Multimodal、AI Governance、Predictive AI/MLOps、Prompt Engineering、Fine-tuning 和 LLM Training 尚未进入场景路径。

### 2.3 中文单线边界

本阶段必须：

- 不修改 app/en/** 和 app/i18n/en/**。
- 不依赖英文问题 ID 解析中文问题。
- 不改变正式问答数量、顺序、证据关系或 addedAt。
- 共享 React 组件只增加有默认值的可选能力。
- 新样式限定在中文首页或中文问题页作用域。
- 保持现有英文构建和页面回归通过。

### 2.4 Stage 0 输入

原计划要求 Stage 1 只消费 Stage 0 已完成用户裁决的下游包：

- `question-candidates`。
- `phrase-candidates`。
- `fallback-triggers`。
- `path-patterns`。
- 对应候选的 `candidateId`、当前位置、owner、风险和用户裁决。
- `needs-answer-rewrite`、`needs-new-qa` 和 `needs-research` 分流结果。

允许进入本阶段的主要是：

- 已批准的 `expression-only` 候选。
- 当前内容已覆盖，但值得增加现场入口的正式问题。
- 已有正式答案支持的兜底触发和路径模式。

Stage 1 也可以从当前库补充独立的现场精选，但必须登记 `selectionOrigin=current-library-curation`、选择理由、正式问题引用、场景、意图和去重依据。这只是取用改进，不改变 Stage 0 的跨库差异结论。

历史执行说明：本分支实际在 Stage 0 尚有 492 项 pending 时进入后续阶段，因此下面启动门没有被满足。当前保留它作为未来流程要求，不把既有 Stage 1 产物说成由完整 Stage 0 授权；已经实现的现场入口改由正式问题映射、当前内容 owner、风险边界和全量页面测试独立复核。

### 2.5 启动门（未来批次）

只有同时满足以下条件才进入实施：

1. Stage 0 已完成，现场备战与表达候选已经用户 Review。
2. 待实施口语、路径和兜底触发项已经获准进入 Stage 1。
3. 核心题候选可以精确映射到当前中文正式问题。
4. 内容 owner 和全局呈现 owner 均已解决。
5. 高风险、动态或需要改写的候选已经分流，不混入本阶段。
6. 当前分支为 `codex/ai-knowledge-base-content-improvement`，且 `HEAD`、正式问题数量、顺序和关键文件摘要已经重新冻结。
7. 英文内容目录摘要已经记录，用于实施后零变化核验。

输入缺少正式问题映射、用户裁决、owner 或风险结论时，退回补齐 Stage 0，不在本阶段建立影子差异矩阵。

## 3. 总体设计

采用“中文现场元数据覆盖层”：

- 不复制正式问题和答案。
- 不给 320 道问答批量增加正文型字段。
- 正式回答、证据和模块上下文继续只来自内容注册表。
- 中文元数据只维护问题意图、现场层级、客户措辞、场景关联和内部选择理由。
- 元数据必须 fail-fast 解析到现有正式问题，不能静默漂移。

## 4. 信息架构

### 4.1 中文首页

建议保持：

1. Hero 与全局入口。
2. 按可用时间开始。
3. 从客户场景开始。
4. 问题搜索和模块目录。
5. 核心术语。

首页只承载全局入口与路径，不展示模块正文、完整问题答案或来源详情。

### 4.2 中文问题页

/questions 调整为：

1. 页面说明和内容规模。
2. 现场使用说明及四类兜底话术。
3. 核心题、全部题、模块和问题意图筛选。
4. 唯一一份正式问题列表。

核心问题只是一种筛选状态。可以提供标题索引和快捷入口，但不能复制完整答案卡片。

### 4.3 单道问题

原有问题卡继续展示：

- 模块与原细标签。
- 正式问题和 addedAt。
- 正式短答、深答、下一问和证据。
- 原模块入口。

现场题可以额外显示：

- 稳定问题意图。
- 核心必答或场景重点标记。
- 一条代表性客户原话。

客户原话是搜索与识别元数据，不是新事实或新答案。

### 5.1 分类方法

- 保留正式问答原有 tag。
- 建立 tag 到 intentId 的默认映射。
- 少量问题允许问题级覆盖，用于同名标签在不同语境中的差异。
- 每道正式问题必须且只能解析出一个主要意图。
- 问题级例外必须登记问题文本与理由。

### 5.2 分类门禁

自动检查：

- 八个意图 ID 唯一、稳定。
- 所有现有 tag 都能映射。
- 映射表没有失效 tag。
- 每道问题只解析出一个主意图。
- 新正式 tag 没有映射时立即失败。
- 问题级覆盖与预期问题文本不一致时立即失败。

## 6. 中文现场元数据契约

建议新增 app/question-field-kit.mjs。该文件只保存取用元数据，不保存正式答案。

每项现场问题记录至少包含：

| 字段 | 作用 |
| --- | --- |
| fieldId | 现场层稳定语义 ID |
| questionRef | `moduleId + questionNumber + expectedQuestion` |
| contentOwnerModuleId | 正式答案、证据和问题判断的模块 owner |
| presentationOwnerId | 固定为 `questions-directory` |
| intentId | 稳定问题意图 |
| tier | core 或 situational |
| scenarioIds | 适用客户场景 |
| customerPhrases | 客户自然说法 |
| displayPhrase | 可选；获准公开显示的一条代表性口语 |
| selectionOrigin | `stage-0-candidate` 或 `current-library-curation` |
| sourceCandidateIds | 对应 Stage 0 候选；当前库精选时可为空 |
| rationale | 内部选择理由，不进入公开 HTML、搜索索引或客户端 props |

正式答案的 owner 不会因为进入全局问题目录而转移；问题目录只负责发现、筛选和呈现。

### 6.1 解析规则

- 使用 `questionRef` 中的 moduleId 和 questionNumber 定位正式问题。
- 同时校验 `expectedQuestion`。
- 模块不存在、序号越界或文本不符时构建失败。
- 保留现有问题锚点，避免旧链接失效。
- 为现场题增加 field-question-{fieldId} 稳定锚点。
- 首页和快捷入口优先链接现场稳定锚点。

本阶段不迁移全部 320 道中文问题的原生 ID。全库问题 ID 迁移如有必要，另立基础设施计划。

### 6.2 禁止重复内容

现场元数据不得保存：

- answer 或 shortAnswer。
- depth。
- ask。
- basis。
- evidence。

页面只能从 app/question-index.mjs 解析后的正式问题读取这些内容。

运行时元数据分成四个受控集合：

- `intentDefinitions`。
- `tagIntentMap` 与少量 `questionIntentOverrides`。
- `fieldQuestions`。
- `fallbackScripts`。

中文首页路径单独由 `home-learning-paths.mjs` 管理。所有集合都必须经过引用完整性检查；`rationale`、Stage 0 候选备注和内部风险说明不得进入公开渲染数据。

## 7. 核心问题选择

### 7.1 硬门

候选必须同时满足：

1. 已进入正式内容注册表。
2. 题内证据能解析到集中 Reference。
3. 短答脱离完整章节仍能理解。
4. 下一问可以继续客户发现。
5. 会改变选型、架构、成本、验收、运营或治理判断。
6. 不依赖过期或边界不清的动态事实。
7. 与其他核心候选不是同一决策的重复表达。

如果短答不适合现场使用，该题进入第 2 阶段改写候选；本阶段不增加 compactAnswer。

### 7.2 人工选择维度

- 跨客户复用频率。
- 决策影响和错答风险。
- 是否暴露关键前提。
- 是否自然进入下一问。
- 是否补足问题意图。
- 是否支持主要客户场景。
- 是否代表当前库独有优势。

### 7.3 数量边界

- 建议 24～40 道，但不是排版配额。
- 可分 core 与 situational。
- 不按 21 个模块平均分配。
- 不按八个意图凑相同数量。
- 同一决策只保留一个主入口。

### 7.4 写入前 Review

先交付：

- 核心候选表。
- owner、意图、场景和选择理由。
- 客户口语候选。
- 排除的高频问题及理由。
- 需要进入第 2 阶段改写的短答。

用户确认后才写现场元数据。

## 8. 客户口语别名

### 8.1 编写规则

每条别名必须：

- 是客户可能真实使用的表达。
- 与正式问题判断范围一致。
- 不暗示正式答案不支持的结论。
- 不增加数字、产品能力或法律判断。
- 不使用内部维护语言。
- 不合并多个独立问题。

### 8.2 搜索规则

客户口语追加到 `/questions` 和中文首页共用的问题搜索投影，并沿用当前搜索匹配行为。

本阶段只验证：

- 完整客户短语可以命中预期问题。
- 短语中的关键技术词可以命中。
- 首页和问题页使用同一份别名投影。

Unicode 归一、分词、模糊匹配、向量搜索或外部搜索服务属于后续搜索增强，不与现场层绑定实施。

### 8.3 冲突门

- 同一标准化别名映射到过多问题时人工 Review。
- 宽泛别名允许命中少量不同责任层的问题，但必须登记理由。
- 别名不能改变正式问题去重测试。

## 9. 四类兜底话术

每类包含 ID、触发条件、可直接说的话、需继续确认的信息、不可越过的边界和推荐入口。

### 9.1 场景和规模不足

用于“能不能做、多少钱、要多少卡”等缺少任务、数据、规模和 SLO 的问题。必须先确认业务结果、数据来源、用户并发、输入输出分布、责任主体和验收条件。

### 9.2 动态事实待核验

用于价格、版本、区域、配额、平台能力和法规状态。必须区分稳定方法、当前快照、核验日期和需要重新打开的官方来源，不能凭记忆给当前值。

### 9.3 法律、安全和高影响责任

先识别场景、主体和数据流，提供工程与治理分诊，并说明何时交给法律、安全或业务责任人复核。不得替代专业意见或绝对归责。

### 9.4 技术成功但业务状态未知

区分协议状态、技术执行状态和权威业务状态，说明查询、幂等、补偿和人工接管，不能把返回字符串当成业务完成证明。

## 10. 问题页交互

### 10.1 主筛选

- 搜索。
- 全部问题或现场精选。
- 模块。
- 八类问题意图。
- 当前结果数量。
- 清除筛选。

原细标签继续显示并进入搜索，但不再进入全站主要分类下拉框。

### 10.2 过滤契约

QuestionDirectoryFilterItem 增加可选字段：

- intentId。
- isFieldKit。
- tier。

筛选可组合 query、moduleId、intentId、view 和 tier。

### 10.3 稳定入口

本阶段必须支持：

- 原有正式问题锚点继续有效。
- 现场题稳定锚点 `field-question-{fieldId}`。
- 中文首页可以进入 `/questions?view=field-kit`。
- 非法 `view` 值安全回退为全部问题。

搜索词、模块和意图的实时筛选暂不写入 URL。完整可分享筛选状态留作后续独立交互增强；搜索框继续提示不要输入客户敏感数据。

### 10.4 渐进增强

- 服务端仍只渲染一份全部问题。
- JavaScript 只负责筛选、URL 和滚动定位。
- 无 JavaScript 时所有正式问题、答案和证据仍可阅读。
- 保留无结果、清除、键盘快捷键、焦点和 aria-live。

## 11. 中文首页时间预算路径

首页并存：

- scenarioLearningPaths：按客户任务。
- timeBudgetPaths：按可用时间。

### 11.1 10 分钟现场速查

找到相关核心问题，准备结论、关键边界和下一问，识别需要使用的兜底话术。

### 11.2 30 分钟会前准备

形成客户目标、三个关键问题、一个主要风险和一个下一步验证动作。

### 11.3 2 小时重点备战

沿一个场景阅读机制、边界、评估和运营内容，形成方案假设、责任边界、PoC 建议和未知信息清单。

### 11.4 系统学习

理解 21 个模块关系，完成至少一个端到端场景蓝图，并建立个人知识缺口清单。可以给建议天数，不承诺统一学习速度。

### 11.5 路径数据契约

建议把中文路径移入 app/home-learning-paths.mjs，包含：

- 稳定路径 ID。
- 时间标签、标题和适用情况。
- 指向问题预设、现场问题、场景路径、模块或实战锚点的步骤。
- 每一步的学习焦点。
- 可观察交付物。

解析时检查所有目标真实存在。

### 11.6 场景路径覆盖

先输出覆盖报告，再判断是否增加：

- 治理与合规落地。
- 模型定制与训练。
- 多模态体验与内容交付。
- 预测式 AI 现代化。

只有形成独立客户任务、学习顺序和交付物时才新增，不为模块覆盖率机械增加路径。

## 12. 中文搜索统一

- 正式问题内容来自 module-content-registry。
- 现场意图、层级和客户口语来自 question-field-kit。
- 首页和 /questions 共用 question-index 的中文搜索投影。
- 首页继续遵守 focused 模块的搜索可见性。
- /questions 继续覆盖全部正式问题。

## 13. 用户 Review 门

### R1：分类与范围

用户确认：

- 八类问题意图是否符合使用习惯。
- `core` 与 `situational` 的含义。
- 24～40 道只作为范围护栏，不作为配额。
- 哪些当前库独有问题值得进入现场集。

R1 通过前不建立运行时元数据。

### R2：现场内容

用户 Review：

- 最终核心题名单及其意图和场景。
- 客户口语别名与允许公开显示的代表性短句。
- 四类兜底话术。
- 排除、暂缓和转入 Stage 2/3 的候选。

R2 通过前不改公开页面。

### R3：路径与页面结构

用户 Review：

- 四种时间预算模式。
- 是否新增场景路径。
- 问题页“全部 / 现场精选 / 意图”的信息层级。
- 本阶段只实现最小稳定入口，不实现完整 URL 筛选状态。

R3 通过后才实施页面和交互。

### R4：实施结果

交付实际文件差异、页面检查结果、自动检查、英文内容摘要零变化证明和 Stage 2/3 交接清单。R4 确认后，只形成专项工作分支检查点，不合并 `main`、不推送、不发布。

## 14. 实施小步

### 1A：分类与候选 Review

只输出八类意图、完整 tag 映射、问题级例外、核心候选、客户口语、兜底话术、时间路径和场景覆盖报告；不改代码，并完成 R1/R2。

### 1B：中文元数据契约

R2 通过后建立现场元数据、fail-fast 解析、稳定现场锚点和元数据测试。

### 1C：问题页改造

R3 通过后增加现场说明、兜底话术、意图筛选、现场预设、最小稳定入口和核心标记，仍只渲染一份正式问题列表。

### 1D：首页学习入口

## 16. 自动检查

### 元数据

- 意图和 fieldId 唯一。
- 所有问题解析出一个意图。
- 所有 tag 有映射。
- 现场题精确绑定正式问题。
- expectedQuestion 一致。
- 现场元数据不含答案和证据副本。
- 场景与路径 ID 有效。
- `sourceCandidateIds` 能解析到 Stage 0 规范候选；当前库独立精选有明确理由。
- `contentOwnerModuleId` 与正式问题模块一致。
- `presentationOwnerId` 固定为 `questions-directory`。
- `rationale` 不出现在公开 HTML 或客户端数据。
- 当前问题键、锚点、数量和顺序保持不变。

### 搜索与筛选

- 客户口语命中预期问题。
- 搜索、模块、意图和现场预设可组合。
- 宽泛别名多命中已 Review。
- `view=field-kit` 可恢复，非法 `view`、清除和无结果行为正确。
- 首页和问题页搜索结果一致。

### 渲染与访问

- 服务端仍渲染全部正式问题。
- 每道完整问题卡只出现一次。
- 原锚点和现场稳定锚点可达。
- 首页不渲染模块正文和维护说明。
- 桌面、平板、手机无溢出。
- 键盘、焦点、表单标签和 aria-live 完整。

### 英文兼容

- 英文内容文件摘要未变化。
- 英文模块、问答、证据和日期门禁通过。
- 英文页面不显示中文现场元数据。
- 英文页面不误报本轮中文同步。

## 17. 日期规则

本阶段默认不修改正式问答或模块知识内容：

- 不刷新模块 updatedAt。
- 不新增或修改问题 addedAt。
- 不触发英文内容同步。

需要改写的正式短答转入第 2 阶段，不在现场层复制答案。

## 18. 对 Stage 2 与 Stage 3 的交接

Stage 1 只发布 `ready-existing-qa` 的现场精选。以下项目不得通过旁路字段留在 Stage 1。

交给 Stage 2：

- `needs-answer-rewrite` 或 `needs-new-qa`。
- 现有下一问不具备客户发现价值。
- 证据足够，但机制、边界或验收表达不完整。
- 正式问题重复、内容 owner 不清或需要正文整合。

交给 Stage 3：

- 法规、数据跨境、事故责任和高影响自动化。
- 价格、版本、地域、配额和平台能力。
- 需要官方法源或动态 Claim 的口语与路径候选。
- 当前证据不足以安全回答的中国交付问题。

每项交接至少包含 Stage 0 `candidateId`、当前正式问题引用或建议 owner、未通过现场硬门的原因、客户场景与意图、缺少的内容维度、日期影响和可能的问答结构影响。

Stage 2 或 Stage 3 完成正式改写后，相关问题不会自动进入现场集，必须重新通过正式问题映射、现场准备度、别名安全和用户 Review。交接清单只记录待办与理由，不成为新答案或预先批准记录。
